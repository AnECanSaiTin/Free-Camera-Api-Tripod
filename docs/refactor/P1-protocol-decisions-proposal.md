## 总体建议

现在确定影响公开接口、数据结构和可观察行为的规则；具体算法、性能参数及兼容矩阵留到对应 core 批次验证。不建议将全部协议延后，否则 storage、editor、EditTools 可能先依赖一套接口，再因实现需求返工。

## 1. document 提交

### 建议现在确定

- 保留同步 `submit`。
- 监听通知期间的重入写入明确拒绝；另提供延迟提交入口，在通知结束后执行并重新检查基版本。
- 提交携带不可变动作标签，供撤销历史使用；不必将标签塞进每种 EditOp。

### 留到实现时确定

队列实现、调度器、线程检查以及延迟结果的通知方式。

### 取舍说明（推荐已确认）

这是对原“回调期间请求排队”规则的进一步调整。同步返回接口不能等待同一线程上尚未执行的队列任务；推荐显式区分同步提交和延迟提交，避免隐式行为。

- [x] 接受推荐方向

## 3. 试算

- `FAILED` 必须包含错误诊断。

## 6. 空间与姿态错误

### 建议现在确定

- 空间解析采用“不需要 / 成功 / 失败”三态，失败携带结构化诊断。
- 姿态各轴明确区分 `ABSENT / VALUE / ERROR`，任一实际依赖错误阻止姿态合成或应用。
- 推荐位置和旋转使用轴级采样结果；存在掩码作为派生查询，不独自承担错误表示。
- 明确 FOV 错误与整姿态诊断的汇总规则。

### 留到实现时确定

## 7. playback 启动与执行

### 建议现在确定

- `start` 先校验请求并准备初始运行条件，成功后才换档和切换播放状态。
- 准备失败不破坏原文档及原播放状态。
- 事件从捕获快照解析，按发生顺序分发。
- 在展开区间、生成事件时就限制预算，不等全部展开后才检查。
- 执行器异常报告已发生的部分执行，并终止后续执行；不承诺回滚宿主副作用。

### 留到实现时确定

执行器注册、循环展开和时间推进算法。

### 已确认方向

- [x] 接受推荐方向
- [ ] 采用其他启动失败或状态切换策略
- [ ] 暂缓

## 8. 接管边界

### 建议现在确定

- 推荐主线程协调。
- 每帧捕获获胜声明并调用其 provider 一次。
- 本次捕获期间发生的登记或释放影响下一次捕获，当前返回已捕获结果。
- provider 不得触发文档发布或嵌套捕获；异常转为本帧准备失败。
- 释放后的新调用和旧缓存复用仍须禁止，明确与“已开始捕获”结果的区别。

### 留到实现时确定

令牌存储、每帧缓存、线程和重入检测。

### 备选说明（捕获边界方案已确认）

推荐方案按捕获边界生效。若更重视释放立即阻止当前帧应用，也可采用“返回前重新检查，失效则丢弃”的策略，但须定义本帧如何报告及后续相机控制行为。

本条是待选线性化规则，不是现有仲裁实现已经完成的事实。

- [x] 接受捕获边界生效方案
- [ ] 采用返回前重新检查、失效丢弃方案
