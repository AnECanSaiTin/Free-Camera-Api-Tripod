## 表达式求值器设计对比评估（只读，未改代码）

对比对象：本项目的 `api/animation/expression/Expression`（闭包编译型求值器） vs `D:\Project\JAVA\jep`（Lexer + Parser + AST + 类型化 Interpreter）。

结论要点（供后续决策参考）：
- 本项目：递归下降解析 + 直接编译成 `Formula` 闭包树 + `ConcurrentHashMap` 文本缓存（上限 512，满了整体清空），单一 float 语义，无 boxing。
- jep：经典三段式 Lexer(800行) → Token 列表 → Parser(优先级爬升) → 类型化 AST → 8 个 Evaluator 做 AST 遍历求值，**没有任何编译缓存**（Main 每次都 new Lexer 重扫字符串）。返回 `Object`，大量 boxing。
- 性能判断：本项目在热路径（每帧每关键帧求值）明显更快；jep 若要用于同样场景必须补编译缓存，否则每帧重复 lex+parse。
- 功能判断：jep 表达力强（类型系统/JLS 类型提升/位运算/三元/字符串），但 Parser 目前只实现表达式，statement 节点（If/For/While/Class）已定义未接线。
- 未修改任何文件，仅评估。

## 闭包树 lambda 开销追问（只读，未改代码）

用户问：`(a,b)->a+b` 与 `(c,d)->c+d` 能否被合并/优化。

**更正上一节的判断**：先前说"512 条缓存 × 每树 N 个 lambda → 元空间泄漏"是**说过头了**。
Java lambda 的类由 `invokedynamic` 按**调用点（源码位置）**生成并链接一次，不是按捕获值生成。
`Expression.java` 里约 40 个 lambda 书写位置 = 约 40 个类，与缓存多少条公式无关；实例才是按公式分配。
所以元空间是**有界**的（约 40 个类），不是泄漏。真正的问题不是分配量，而是：

1. **megamorphic 派发**：`Formula.evaluate` 有约 40 个实现者，闭包树里每个 `left.evaluate(r)` 调用点
   在运行期看到几十种 receiver → C2 无法内联（超过 2 个 receiver 就退化成 itable 查找）。
   每帧每节点一次接口派发，这才是热路径的实际成本。
2. **双重间接**：内置一元/二元函数还多套了一层 `FloatOperator` / `FloatPairOperator`。

Java 层面**无法**做 lambda 的结构化去重（`LambdaMetafactory` 以调用点为 key）。
要"合并"只能把差异从**代码**变成**数据**：改成指令数组（int[] ops + float[] consts + switch 循环）
或 AST 节点带 int opcode 字段 + 单一 switch 求值器。这样才可哈希共识（hash-consing）复用子树。

建议优先级（未实施）：① 去掉 FloatOperator 间接层；② 常量折叠；③ 指令数组化（收益最大，也最费工）。

## 动态关键帧（值源/表达式）改造的耦合度评审（只读，未改代码）

通读 `src/main/java`，重点看了 `api/animation/{curve,expression,track,path}` 与 `core/{cmd_camera/playback,editor}`。

已确认的结构性问题（后续若要重构，从这里入手）：
1. **包级依赖环**：`curve.Curve` import `expression.Solver`；`expression.ExpressionSolver` import
   `animation.CameraAnimationc` + `curve.Curve` + `track.CurveTrack`。curve ↔ expression 双向依赖。
2. **同一份曲线两个容器**：`Clip.curves` 与 `CameraAnimation.tracks`，增删改名都要同步维护两处
   （`addChannel`/`removeChannel`/`renameCurveTrack`/`copyFrom`）。
3. **"是否带求解器"没有统一规则**：播放器 `CameraPlayer` 带、`GraphPanel.renderCurve` 与
   `CurveTrack.addKey` 不带 → 图上画的/插键取的是回退值，与播放结果不一致；`Curvec` 只读接口
   根本没有带求解器的重载，外部界面后端（`api.editor.EditorSession`）拿不到动态值。
4. **`CameraAnimation` 职责过多**（685 行）：通道/顺序/变量表/函数表/模式换算/引用完整性
   （`renameCurveTrack` 改 `TrackValue`、`unbindVariables`）/自嵌套静态分析（`selfReferencing` 里
   扫曲线每键 5 个值源 + `Expression.references` 字符串匹配）。
5. **两套环检测**：`VariableGraph`（静态图）与 `ExpressionSolver.visiting`（运行期栈）语义需保持一致。
6. **求解器生命周期靠"按帧 new"**：`EditorContext.beginFrame()`+`frameSolver`，而
   `ExpressionEditorWindow.solver()` 另起一份；漏调不会算错、只显示旧值（注释已自认）。
7. **`Solver` 一接口身兼四职**：变量解析 + 环境量(t/p/wt) + 轨道读数 + 函数查询 + 环诊断 `cycle()`。
8. **热路径开销**：`ExpressionSolver.findCurve` 每次线性扫 `animation.curveTracks()`（该方法每次
   `List.copyOf`），且 `curveCache.computeIfAbsent` 返回 null 不落缓存 → 找不到时每次重扫；
   `VariablePanel.valueInvalid` 每帧每行调 `selfReferencing`（全曲线扫描）。

给用户的建议主线：**把动态求值从插值内核挪出去，改成"每帧一次解析/烘焙 + 纯 float 插值"**
（`EvaluationScope` + `CurveSampler`），`Curve`/`Clip` 签名里的 `@Nullable Solver` 随之消失；
再把变量表/函数表抽成 `SymbolTable`，引用完整性由它自己维护。详见当次对话结论。
