## 【重要】指令数组化实测：负优化，已回退

按上面第 ③ 条把 `Expression` 改成了「递归下降 → 扁平指令数组 + switch 循环 + float[] 栈」，
并做了差分测试 + 吞吐基准。**结论：比原闭包树慢 2~3 倍，已 `git checkout` 回退，工作区干净。**

实测数据（JDK 25 / HotSpot，取 5 轮最快，单条公式求值耗时）：

| 公式条数 | 闭包树 ns/op | 指令数组 ns/op | 比值 |
|---|---|---|---|
| 1   | 7.77  | 22.79 | 0.34 |
| 4   | 8.08  | 36.00 | 0.22 |
| 16  | 11.99 | 31.21 | 0.38 |
| 64  | 13.22 | 31.83 | 0.42 |
| 256 | 13.66 | 32.92 | 0.41 |

诊断补充：
- 关掉 `-XX:-DoEscapeAnalysis` 和 `-XX:-TieredCompilation`，指令数组都是 ~26~27 ns，
  **说明慢不是 `new float[stackSize]` 的分配**（逃逸分析本就没起作用），而是解释器循环固有开销：
  每条指令一次 switch 间接跳转（分支预测失败）+ 数组栈读写。
- 闭包树 1→256 条只涨 1.75 倍，说明"超多态派发"确实存在但代价有限（约 6ns 全公式摊薄）；
  HotSpot 对少量 receiver 的直接调用 / 内联远好于数据驱动的间接跳转。

**结论（供以后参考，别再重复这个尝试）**：
本项目的表达式求值不要换成 switch 解释器。要提速只有两条路——
① 生成真正的 JVM 字节码（需 ASM，改动大）；② 恒等优化（常量折叠）收益有限因为公式多是变量驱动。
真正的每帧大头是 `CameraPlayer.java:93` / `EditorContext.java:213` 每帧 `new ExpressionSolver`（4 个 HashMap/Deque）。

差分测试方法（可复用）：把旧实现改名 `ExpressionOld` 放同包，两边各配一套 Resolver，
比对 ① 编译是否成功 ② `Float.compare` 结果（NaN 算相等）③ 变量被取值次数（验证按名绑定语义）。
本次 178 项检查全过，唯一差异：旧实现的 `smoothstep` 把 edge0 求值了两次（新实现只一次，结果值一致）。

## 动态关键帧（值源/表达式）改造的耦合度评审（只读，未改代码）

通读 `src/main/java`，重点看了 `api/animation/{curve,expression,track,path}` 与 `core/{cmd_camera/playback,editor}`。

已确认的结构性问题（后续若要重构，从这里入手）：
1. **包级依赖环**：`curve.Curve` import `expression.Solver`；`expression.ExpressionSolver` import
   `animation.CameraAnimationc` + `curve.Curve` + `track.CurveTrack`。curve ↔ expression 双向依赖。
2. **同一份曲线两个容器**：`Clip.curves` 与 `CameraAnimation.tracks`，增删改名都要同步维护两处
   （`addChannel`/`removeChannel`/`renameCurveTrack`/`copyFrom`）。
3. **"是否带求解器"没有统一规则**：播放器 `CameraPlayer` 带、`GraphPanel.renderCurve` 与
   `CurveTrack.addKey` 不带 → 图上画的/插键取的是回退值，与播放结果不一致；`Curvec` 只读接口
   根本没有带求解器的重载，外部界面后端（`api.editor.EditorSession`）拿不到动态值。
4. **`CameraAnimation` 职责过多**（685 行）：通道/顺序/变量表/函数表/模式换算/引用完整性
   （`renameCurveTrack` 改 `TrackValue`、`unbindVariables`）/自嵌套静态分析（`selfReferencing` 里
   扫曲线每键 5 个值源 + `Expression.references` 字符串匹配）。
5. **两套环检测**：`VariableGraph`（静态图）与 `ExpressionSolver.visiting`（运行期栈）语义需保持一致。
6. **求解器生命周期靠"按帧 new"**：`EditorContext.beginFrame()`+`frameSolver`，而
   `ExpressionEditorWindow.solver()` 另起一份；漏调不会算错、只显示旧值（注释已自认）。
7. **`Solver` 一接口身兼四职**：变量解析 + 环境量(t/p/wt) + 轨道读数 + 函数查询 + 环诊断 `cycle()`。
8. **热路径开销**：`ExpressionSolver.findCurve` 每次线性扫 `animation.curveTracks()`（该方法每次
   `List.copyOf`），且 `curveCache.computeIfAbsent` 返回 null 不落缓存 → 找不到时每次重扫；
   `VariablePanel.valueInvalid` 每帧每行调 `selfReferencing`（全曲线扫描）。

给用户的建议主线：**把动态求值从插值内核挪出去，改成"每帧一次解析/烘焙 + 纯 float 插值"**
（`EvaluationScope` + `CurveSampler`），`Curve`/`Clip` 签名里的 `@Nullable Solver` 随之消失；
再把变量表/函数表抽成 `SymbolTable`，引用完整性由它自己维护。详见当次对话结论。

## 第 1 步改造已实施（本次实际改了代码）

用户选择：只做第 1 步 + 直接删掉旧签名。已落地，编译通过。

新增 `api/animation/eval/`：
- `Scope`（原 `expression/Solver`，extends `Expression.Resolver`，新增 default `evaluate(String)`）
- `ExpressionScope`（原 `ExpressionSolver`）：`track(id)` 改用 `StaticKeys` 求值；每条曲线配一份静态
  读取器缓存在 `IdentityHashMap<Curve, KeyValues>`
- `ResolvedKeys implements KeyValues`：按 Scope 惰性解析 5 个字段，`float[]` 按 (键,字段) 缓存，
  **换 curve / 键数变化 / 换 scope 三者任一即清空**（scope 带时间 → 自动按帧失效）
- `CurveSampler`：**求值唯一入口**。`sample(curve,time,scope)`（复用缓存）/ `sampleOnce`（不复用）/
  `sampleStatic`（只读固定值）/ `sample(clip,time,Evaluator,scope)`

`api/animation/curve/`：
- 新增 `KeyValues` 接口（按 index 读 5 个数值）+ `StaticKeys` 实现。放 curve 包是为了让
  `eval → curve` 单向依赖，curve 不认识 eval（包环就此解开）
- `Curve.evaluate(float, KeyValues)` 取代 `evaluate(float)` / `evaluate(float, Solver)`；插值内部改用 index+values
- `Curvec.evaluate` 同步改签名
- `Clip` 变成纯容器：三个 `evaluate` 重载全删（取值走 CurveSampler）

`Keyframec` 新增 5 个 `xxxSource()`（Keyframe 原本就有实现），只读视图才能参与动态求值。

调用点：`CameraPlayer` 改用 `ExpressionScope + CurveSampler`（sampler 是实例字段）；
`EditorContext.solver()→scope()` 且新增 `sampler()`，`beginFrame` 一并 clear；
`GraphPanel.renderCurve` 改走 sampler（**修掉"曲线图画的是回退值、与播放不一致"**）；
`AnimationTrack` 新增 default `addKey(time, Scope)`，`CurveTrack` 重写（按公式值插键），
`CameraEditorModel.addKey` 加 Scope 参数，5 处调用点传 `context.scope()`。
