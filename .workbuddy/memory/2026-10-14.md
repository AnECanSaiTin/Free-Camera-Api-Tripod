## 评审 docs/design-animation-editor-framework.md（相机动画/播放/编辑器重构框架）

结合代码核对了文档断言，产出评价（未改任何代码/文档）。核心结论：

- 文档对现状的诊断准确：CameraAnimation.java:469 copyFrom 不能换对象、EditorHistory 64 快照 + 250ms 节流、
  CameraPlayer.java:52-79 回绕/末尾、:100-124 未接管轴沿用玩家坐标、CameraEditorScreen.java:1240 硬编码兜底、
  AnimationCodec 第 66 行"反序列化一律宽松"、run/camera_animations 仅 2 个测试文件、EvaluationGraph2 零引用（死代码）。
- 发现的硬问题（已反馈给用户）：
  1. 轨道 id 不能改成 `Identifier`：TimelinePanel.java:1117 用本地化名拼默认名（中文"曲线1"），Identifier path 不接受非 ASCII。
  2. §7.6 `CameraControlClaim.overridePose()` 返回 `LocalPose` 是类型级错误——自由视角是世界姿态（CmdCamera.java:61-64 直接当世界姿态用）。
  3. §6 Codec 未说明 `CurveTrack` 的 label/color 是 AnimationChannelRegistry 派生物（CameraAnimation.java:95-97 / AnimationChannelRegistry.java:79 兜底）。
  4. §2.4 字段名判据与 §6.3"诊断模式"自相矛盾。
  5. §4.3/附录C 的 Vec3 返回式变换签名会破坏现有零分配求值路径（CameraPlayer posCache / RotEvaluator）；建议 dest-passing + joml Vector3f。
  6. §5.5 撤销走校验可能让历史旧版本过不了新规则；§4.4 降级"最近已知位置"优先会导致镜头跳变。
- 规模数据修正：core.editor 实际 44 文件 / 16,948 行（文档写 13,162）；"4,910 行"是 api 整包而非 api.animation（实为 52 文件 / 6,157 行）。
- 迁移顺序建议：G7（AnimationPlayer 提到 api、可单测）应提前到 P0 之后——全仓只有 1 个测试文件且测的是死代码；
  P0 不是"只改包名"，core→core.editor 有 4 条边（CmdCamera / CmdCameraKeyMapping / PathRender / CameraPlaybackClient）。
- 现有 api 已零 net.minecraft.client、零 core/editor 引用（§2.4 前四条判据现状即通过）。

## 项目事实备忘

- 序列化现状是 GSON + `api.animation.JsonSerializable` + 容器 `core.animation.io.AnimationCodec`（594 行，压着 18 个字段名常量）；
  全仓仅 `api/camera/ControlScheme.java` 与 `core/animation/io/AnimationSavedData.java` 用了 `com.mojang.serialization`。
  文档 D7"统一改用 Codec"等于整层重写，不是收尾。
- 存档 SavedData 把动画/路径以 **JSON 字符串** 存进 NBT（`AnimationSavedData` 的 animations/paths 两个 CompoundTag）。
- 值源是 sealed：NumberSource{Constant,Formula} / ValueSource{NumberSource,TrackRef}；`NumberSource.evaluateOrFallback` 是唯一回退点。
