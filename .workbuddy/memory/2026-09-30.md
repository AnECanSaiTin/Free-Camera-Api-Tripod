## 方案评估：让 Keyframe 缓存 Scope、Keyframec 不再暴露 ValueSource（结论：不采纳）

用户提出：把 5 个 `xxxSource()` 从 `Keyframec` 撤掉，改成 `Keyframe` 字段下缓存一个 `Scope`，
每帧求值前先更新它（动机大概率是 9-28 记录里那条"每帧 new ExpressionScope"的热路径开销）。
通读 `ResolvedKeys` / `KeyValues` / `StaticKeys` / `Keyframe` / `EditorContext` 后给出的结论：
**动机成立，手段不合适**——同样的收益有代价小一个数量级的做法。

否掉的理由（按严重程度）：

1. **毁掉"两种取值口径"这条关键约定（最致命）**。`KeyValues` 有两个实现不是巧合：
   `StaticKeys` 只读固定值，变量读轨道走的正是它，靠这个躲开"变量绑的轨道又引用该变量"的无限递归
   （`StaticKeys` 类注释第 5-9 行）。求值一旦塞进 Keyframe，键只知道"按自己的 Scope 算"，
   静态口径就没了，只能退化成给键加一个"当前是否静态"的开关 → 自嵌套保护出问题。
2. **"不暴露 ValueSource" 与 "键自己求值" 是同一个决定的两面**，没有第三条路：
   求值必须知道公式是什么，要么外部读取器读 `xxxSource()`（现状），要么键自己算（提案）。
   选后者 = 把 `ResolvedKeys` 的职责搬进 Keyframe，键从"纯数据"变成"认识 Scope、会求值、带缓存"，
   **方向正好与 9-28~29 那四步重构相反**（那四步的主线就是把动态求值从数据里挪出去）。
3. **`ResolvedKeys.reset` 的缓存失效判定是引用比较**（`ResolvedKeys.java:42` 的 `this.scope != scope`）。
   这依赖"Scope 不可变、带时间、每帧换一个新的"。提案隐含可变复用 Scope，
   同一对象只改时间 → 失效判定立刻不成立 → 曲线拿上一帧解析出来的数接着用。**真做必须一起改**。
4. **每帧更新变成 O(键数) 写入**。现状是一帧 new 1 个 Scope + `ResolvedKeys` 惰性解析（一次采样只碰
   区间两端的 2 个键）；提案要每帧把所有键的 Scope 字段刷一遍，200 键的曲线就是 200 次写。
   若"键上的 Scope 其实是同一个共享引用"，那它等价于"Scope 挂在动画/Curve 上"，
   跟挂在播放器/EditorContext 上没有区别，却给 Keyframe 多塞了一个非数据字段。
5. **缓存字段混进数据对象**：Keyframe 是可变共享对象（`Curve.key(int)` 直接给内部实例），
   `Keyframe(Keyframec)` 构造、`set()` 覆盖拷贝、撤销栈快照、剪贴板 `CameraEditorScreen.KeyClip`、
   序列化都要逐个回答"拷不拷这个字段"。拷了会拖住旧 Scope 引用（连带整个动画与变量表）；
   不拷则粘贴/撤销恢复出来的键没有 Scope，求值静默退化成回退值——**正是 9-28 修掉的那类
   "图上画的值与播放不一致"**。
6. **"取值一律走 CurveSampler" 这个硬约束会被拆散**：现在想求值必须给 Scope，编译期就保证；
   改成键自己求值后，"有没有刷新 Scope" 变成每个持有键的地方各自的自觉，漏了只在用了公式时才暴露。

给出的替代方案：

- **A（推荐）可变复用 Scope**：给 `ExpressionScope` 加 `time/progress/worldTime` 的 setter
  或 `reset(time, worldTime)`，播放器与 `EditorContext` 复用一个实例；**同时**把 `ResolvedKeys`
  的失效判定从引用比较换成显式的帧版本（`Scope.version()` 单调递增）。省掉每帧 6 个集合的分配，
  `ResolvedKeys` 惰性缓存、`StaticKeys` 静态口径、CurveSampler 唯一入口全部保留。
- **B（若诉求其实是接口干净）收窄暴露面**：把 5 个 `xxxSource()` 从 `Keyframec` 挪到一个更窄的接口
  （例如 `DynamicKeys`），由 `Curvec#sources()` 给出（无公式时返回 null）。只读视图默认看不到值源，
  求值层仍拿得到，`ResolvedKeys` 实现不变。这是"收窄"而不是"把求值塞回键里"。
- **C 先量再改**：9-28 的基准里单条公式求值 7.7~13.7 ns/op；每帧一次 `new ExpressionScope` 是 6 个小
  集合的分配，HotSpot 上大概率是 TLAB 指针碰撞、甚至被标量替换。没有 profile 之前为它动架构不划算。

## 方案 A 已实施（编译通过，提交 466ba9d）：求值环境跨帧复用

实施时发现一个**前提**：`ExpressionScope` 原来在构造时把 `variables()` / `functions()` 抄成自己的两份
`LinkedHashMap`。一旦跨帧复用，这两份就再也不更新了——编辑器里改个变量名、读档换一批变量，
播放取的全是旧名字。所以 A 分两步：

**第一步：符号表自己持有名字索引**（`SymbolTable`）
- 新增 `variablesByName` / `functionsByName` 两张 `HashMap`，与顺序表同步维护
  （add / remove / rename / replaceFrom 六处各自更新）
- `variable(name)` / `function(name)` 由线性扫描变成 O(1)
- 已确认**没有外部代码绕过 `SymbolTable` 直接改名字**（只有 `SymbolTable.java:127/177` 两处调
  `variable.name(...)` / `function.name(...)`），索引不会被外部改坏
- 写 `replaceFrom` 时踩了个坑：一开始把**源对象**塞进索引、副本塞进列表，两份不一致；
  已改成副本进两处（这是 `copyFrom` 不共享实例的硬约定）

**第二步：作用域可复用**
- `Scope` 新增 `long version()`：每换一帧 +1。缓存按它失效，**不再只按对象身份判断**
- `ExpressionScope` 改成 `(SymbolTablec, CurveLookup)` 构造 + `frame(time, progress, worldTime)` 切帧；
  符号表**按引用持有**不抄（抄了就跟不上编辑）；切帧时 `cache.clear()`、`staticKeys.clear()`、
  `cycle = null`、`version++`；`progressOf` 由 private 改 public（调用方要算进度传进来）
- `ResolvedKeys` 失效判定：`curve != || size != || scope != || version !=`。
  **两个都要**：只比身份漏掉"同一对象换了一帧"，只比版本漏掉"两个不同对象恰好版本相同"
- `CameraPlayer` / `EditorContext` 各持有一份 `ExpressionScope`，每帧 `frame(...)`。
  `EditorContext` 用 `frameDirty` 标记 + 懒刷新（`beginFrame` 只打标记，首次用到才切帧，
  这样没人要作用域时一分钱不花）；原先 `beginFrame` 里的 `frameSampler.clear()` 删掉——
  版本号已经能兜住，留着是冗余
- **表达式编辑窗口是唯一例外，故意每帧新建**：暂停时播放头不动，没法用"时间变了"判断
  该不该切帧，而窗口开着时用户随时在改公式与变量，预览必须当帧跟上（注释已写明这个例外）
- 顺带清掉了 `ExpressionScope` 里两张名字 Map（共六个集合 → 四个），并修正了
  `CurveSampler.clear()` 与 guide §5 里"跨帧复用要手动 clear"这条已经过时的说明

收益：播放与编辑器主界面每帧不再分配作用域；`cache` / `staticKeys` 的 Map 跨帧复用桶，
只有 `clear()` 没有重建。`staticKeys` 每帧清空是刻意的——作用域长期存活，不清的话
读档换掉的旧 Curve 会被这张 IdentityHashMap 一直拽着。

## 方案 B 的落地设计（用户要求给出方案，尚未实施）

目标：把 5 个 `xxxSource()` 从 `Keyframec` 上撤下来，求值位置**不动**（仍在 `ResolvedKeys`）。
已核实调用点，只有两处会受影响（`AnimationCodec` 与 `CameraEditorScreen` 用的都是具体
`Keyframe` 类型，不受影响）：

1. 新建 `curve/DynamicKeys`（与 `KeyValues` 对称：一个给"算好的数"，一个给"数怎么来的"），
   5 个 `xxxSource()` 声明在它上面
2. `Keyframe implements Keyframec, DynamicKeys` —— 方法体不动，只是换了个接口声明；
   `Keyframec` 删掉这 5 个（保留 `value()` / `inSlope()` 那组固定数值读法）
3. `Curvec` 新增 `@Nullable DynamicKeys sources(int index)`；
   `Curve` 实现为 `key(index) instanceof DynamicKeys d ? d : null`
   （放在曲线上而不是键上，是因为 `Curvec.key(index)` 返回的是 `Keyframec`，
   可能是没有公式的第三方实现，求值层需要一个"要么给来源、要么明说没有"的入口）
4. `ResolvedKeys.resolve` 改读 `curve.sources(index)`；`SymbolTable.references` 的入参
   从 `Keyframec` 改成 `@Nullable DynamicKeys`（null 即无公式，直接返回 false），
   `CameraAnimation.selfReferencing` 相应改传 `curve.sources(i)`

可顺带做的优化（可选，不属于 B 本身）：`Keyframe.dynamic()` 已经能判断"这个键有没有公式"，
`Curve` 可以据此缓存"整条曲线是否含动态键"，没有就让采样直接走 `StaticKeys`——
绝大多数曲线没有公式，这条路径能省掉整套解析。

## 又一个问题：把 `Keyframec` 的 5 个 float getter 直接改成返回 `ValueSource`（评估：不合适）

问的是"既然每个数值就是一个值源，何不合并成一套 `value() : ValueSource`，两套读写 10 → 5"。
概念上说得通（`Keyframe` 类注释就是这么写的），但**在 `Keyframec` 上做不合适**：

1. **会把 `ValueSource` 倒灌回曲线插值内核（最致命）**。`Curve:211-229` 自动斜率计算读的是
   `next.value() / current.value()`（具体类型是 `Keyframe`），合并后要写 `next.value().constant()`——
   曲线内核从此认识"值源"这个概念，而这正是 9-28 第 1 步"把动态求值从插值内核挪出去、
   曲线退回纯数值插值"要消除的东西。方向相反。
2. **口径选择从接口层散落到调用点**（约 40 处要补 `.constant()`）：
   GraphPanel ~17、Curve 8、`Keyframe` 两个拷贝路径 10、StaticKeys 5、KeyframePanel 5 处取值 +
   5 个 `key::value` 方法引用（getter 与 setter 同名，返回类型还不同，读起来很含混）。
   `float value()` 是**固定数值口径**（几何 / 编辑 / 序列化 / 静态求值），
   `valueSource()` 是**动态口径**，现在靠方法名区分，合并后靠调用方自觉。
3. **选错了不报编译错**：`.constant()` 与 `.evaluate(scope)` 都返回 float，
   只有挂了公式时才会错——正是 guide §5 点名的那类最难查的坑。
4. 与 `KeyValues`（Curve 消费的 float 读取器）不对称，转换点被推散到各处。

结论：想要"方法数少一半"的话，方案 B 更划算——`Keyframec` 只剩 5 个 float getter（干净），
值源挪去窄接口 `DynamicKeys`，只有 `ResolvedKeys` / `SymbolTable` 两处要改，零调用点噪音。
现状 `Keyframec` 暴露 `ValueSource` 本身不算错（能编译能跑），B 是"收窄暴露面"而非"修 bug"。
