# 2026-09-30

## 方案评估：让 Keyframe 缓存 Scope、Keyframec 不再暴露 ValueSource（结论：不采纳）

用户提出：把 5 个 `xxxSource()` 从 `Keyframec` 撤掉，改成 `Keyframe` 字段下缓存一个 `Scope`，
每帧求值前先更新它（动机大概率是 9-28 记录里那条"每帧 new ExpressionScope"的热路径开销）。
通读 `ResolvedKeys` / `KeyValues` / `StaticKeys` / `Keyframe` / `EditorContext` 后给出的结论：
**动机成立，手段不合适**——同样的收益有代价小一个数量级的做法。

否掉的理由（按严重程度）：

1. **毁掉"两种取值口径"这条关键约定（最致命）**。`KeyValues` 有两个实现不是巧合：
   `StaticKeys` 只读固定值，变量读轨道走的正是它，靠这个躲开"变量绑的轨道又引用该变量"的无限递归
   （`StaticKeys` 类注释第 5-9 行）。求值一旦塞进 Keyframe，键只知道"按自己的 Scope 算"，
   静态口径就没了，只能退化成给键加一个"当前是否静态"的开关 → 自嵌套保护出问题。
2. **"不暴露 ValueSource" 与 "键自己求值" 是同一个决定的两面**，没有第三条路：
   求值必须知道公式是什么，要么外部读取器读 `xxxSource()`（现状），要么键自己算（提案）。
   选后者 = 把 `ResolvedKeys` 的职责搬进 Keyframe，键从"纯数据"变成"认识 Scope、会求值、带缓存"，
   **方向正好与 9-28~29 那四步重构相反**（那四步的主线就是把动态求值从数据里挪出去）。
3. **`ResolvedKeys.reset` 的缓存失效判定是引用比较**（`ResolvedKeys.java:42` 的 `this.scope != scope`）。
   这依赖"Scope 不可变、带时间、每帧换一个新的"。提案隐含可变复用 Scope，
   同一对象只改时间 → 失效判定立刻不成立 → 曲线拿上一帧解析出来的数接着用。**真做必须一起改**。
4. **每帧更新变成 O(键数) 写入**。现状是一帧 new 1 个 Scope + `ResolvedKeys` 惰性解析（一次采样只碰
   区间两端的 2 个键）；提案要每帧把所有键的 Scope 字段刷一遍，200 键的曲线就是 200 次写。
   若"键上的 Scope 其实是同一个共享引用"，那它等价于"Scope 挂在动画/Curve 上"，
   跟挂在播放器/EditorContext 上没有区别，却给 Keyframe 多塞了一个非数据字段。
5. **缓存字段混进数据对象**：Keyframe 是可变共享对象（`Curve.key(int)` 直接给内部实例），
   `Keyframe(Keyframec)` 构造、`set()` 覆盖拷贝、撤销栈快照、剪贴板 `CameraEditorScreen.KeyClip`、
   序列化都要逐个回答"拷不拷这个字段"。拷了会拖住旧 Scope 引用（连带整个动画与变量表）；
   不拷则粘贴/撤销恢复出来的键没有 Scope，求值静默退化成回退值——**正是 9-28 修掉的那类
   "图上画的值与播放不一致"**。
6. **"取值一律走 CurveSampler" 这个硬约束会被拆散**：现在想求值必须给 Scope，编译期就保证；
   改成键自己求值后，"有没有刷新 Scope" 变成每个持有键的地方各自的自觉，漏了只在用了公式时才暴露。

给出的替代方案：

- **A（推荐）可变复用 Scope**：给 `ExpressionScope` 加 `time/progress/worldTime` 的 setter
  或 `reset(time, worldTime)`，播放器与 `EditorContext` 复用一个实例；**同时**把 `ResolvedKeys`
  的失效判定从引用比较换成显式的帧版本（`Scope.version()` 单调递增）。省掉每帧 6 个集合的分配，
  `ResolvedKeys` 惰性缓存、`StaticKeys` 静态口径、CurveSampler 唯一入口全部保留。
- **B（若诉求其实是接口干净）收窄暴露面**：把 5 个 `xxxSource()` 从 `Keyframec` 挪到一个更窄的接口
  （例如 `DynamicKeys`），由 `Curvec#sources()` 给出（无公式时返回 null）。只读视图默认看不到值源，
  求值层仍拿得到，`ResolvedKeys` 实现不变。这是"收窄"而不是"把求值塞回键里"。
- **C 先量再改**：9-28 的基准里单条公式求值 7.7~13.7 ns/op；每帧一次 `new ExpressionScope` 是 6 个小
  集合的分配，HotSpot 上大概率是 TLAB 指针碰撞、甚至被标量替换。没有 profile 之前为它动架构不划算。
